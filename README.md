# TestBol QA

Система управления тестированием: проекты, тест-кейсы, тест-прогоны, баг-репорты и вложения. Изменения сразу видны всем участникам.

- **Тест-кейсы** со статусом готовности (черновик / готов / устарел) и последним результатом из прогонов. Кейсы раскладываются по вложенным папкам, перемещаются пачкой, а в прогон папку можно добавить целиком.
- **Тест-прогоны**: набор кейсов, проверяемый на конкретной сборке. Результаты прошлых прогонов не перезаписываются, а в прогоне видно, что было с каждым кейсом в прошлый раз, и отмечены регрессы.
- **Баги** с жизненным циклом Новый → В работе → Исправлен → Проверен → Закрыт (плюс «Отклонён» и «Дубликат»), серьёзностью, исполнителем и окружением. Из упавшего кейса в прогоне баг заводится одной кнопкой, шаги и ожидаемый результат подставляются сами.
- **Комментарии** к багам и тест-кейсам: их пишут все участники проекта, в том числе разработчики.
- **Вложения** (скриншоты, логи) к багам и к результатам в прогонах: можно перетащить файл или вставить скриншот через Ctrl+V.
- **Автотесты**: каждый запуск автотестов (на своём компьютере или в CI) попадает отдельной папкой во вкладку «Автотесты» с результатами и скриншотами падений. Тесты сами заводятся в реестре при первой встрече. Подробнее в части 3.

**Стек:** Node.js 20 + Express, PostgreSQL 16, React 18 + TypeScript (сборка Vite), Docker Compose.

```
testbol-qa/
├── docker-compose.yml     # приложение + PostgreSQL (+ необязательные Cloudflare Tunnel и локальная модель)
├── Dockerfile             # образ приложения
├── .env.example           # шаблон настроек → скопировать в .env
├── server/
│   ├── index.js           # HTTP API: авторизация, проекты, тест-кейсы, общее состояние
│   ├── runs.js            # тест-прогоны и результаты
│   ├── bugs.js            # баг-репорты и их жизненный цикл
│   ├── comments.js        # комментарии к багам и тест-кейсам
│   ├── folders.js         # папки тест-кейсов
│   ├── attachments.js     # загрузка и выдача файлов, очистка «осиротевших» файлов
│   ├── autotests.js       # запуски автотестов, реестр автотестов, токены для скриптов
│   ├── live.js            # живые обновления (Server-Sent Events)
│   ├── llm.js             # локальная языковая модель: запросы, очередь, проверка готовности
│   ├── auth.js            # пароли (bcrypt), сессии в cookie, ограничение попыток входа
│   ├── db.js, migrate.js  # подключение к PostgreSQL и миграции
│   └── migrations/        # схема базы (применяется автоматически при старте)
├── web/                   # интерфейс: React + TypeScript, собирается в public/
│   └── src/views/         # экраны: проекты, кейсы, прогоны, баги
├── docs/API.md            # описание HTTP API: все запросы, поля и ответы
├── scripts/
│   ├── import.js          # перенос данных из прошлой облачной версии
│   ├── playwright-reporter.js  # репортер Playwright: результаты запуска уходят в TestBol
│   ├── report.js          # отправка результатов других фреймворков (JUnit XML)
│   └── backup.sh / .ps1   # резервное копирование базы и вложений
└── import/                # сюда кладётся export.json для импорта (в git не попадает)
```

## Часть 1. Развернуть на своём компьютере

### Шаг 1. Установить Docker и Git

| ОС | Docker | Git |
|---|---|---|
| **Windows 10/11** | [Docker Desktop](https://www.docker.com/products/docker-desktop/). При установке оставьте галочку «Use WSL 2». После установки перезагрузите компьютер. | [git-scm.com](https://git-scm.com/download/win) |
| **macOS** | [Docker Desktop](https://www.docker.com/products/docker-desktop/) (выберите Apple Silicon или Intel) | `xcode-select --install` |
| **Linux (Ubuntu/Debian)** | `curl -fsSL https://get.docker.com \| sh`, затем `sudo usermod -aG docker $USER` и перелогиньтесь | `sudo apt install git` |

Проверка в терминале (на Windows — PowerShell):

```sh
docker --version
docker compose version
git --version
```

Все три команды должны вывести версии. На Windows и macOS Docker Desktop должен быть запущен (иконка кита в трее).

### Шаг 2. Получить код

**Вариант А — из архива.** Распакуйте `testbol-qa.zip` в удобную папку, например `C:\testbol-qa` или `~/testbol-qa`. В архиве уже есть git-репозиторий с первым коммитом.

**Вариант Б — через GitHub** (удобно, чтобы хранить код и обновлять его):

1. На github.com создайте **приватный** репозиторий `testbol-qa` без README.
2. На основном компьютере в распакованной папке выполните:
   ```sh
   git remote add origin https://github.com/<ваш-логин>/testbol-qa.git
   git push -u origin main
   ```
3. На втором компьютере:
   ```sh
   git clone https://github.com/<ваш-логин>/testbol-qa.git
   cd testbol-qa
   ```

Файл `import/export.json` с данными из прошлой версии в репозиторий не попадает (в нём хэши паролей). Если нужен импорт, скопируйте его на второй компьютер в папку `import/` вручную.

### Шаг 3. Создать файл настроек `.env`

```sh
# Linux / macOS
cp .env.example .env
# Windows (PowerShell)
Copy-Item .env.example .env
```

Откройте `.env` в блокноте и замените `POSTGRES_PASSWORD` на длинный случайный пароль. Сгенерировать можно так:

```sh
# Linux / macOS
openssl rand -base64 24
# Windows (PowerShell)
[Convert]::ToBase64String((1..24 | % { Get-Random -Max 256 }))
```

Важно: пароль базы задаётся **один раз** при первом запуске. Если поменять его потом, приложение не подключится к уже созданной базе.

### Шаг 4. Запустить

В папке проекта:

```sh
docker compose up -d --build
```

Первый запуск занимает 1–3 минуты: скачиваются образы Node.js и PostgreSQL. Проверьте, что всё поднялось:

```sh
docker compose ps
docker compose logs app
```

В логах должна быть строка `TestBol QA запущен: http://localhost:3000`.

### Шаг 5. Открыть приложение

Откройте в браузере **http://localhost:3000** и зарегистрируйте первого пользователя — он станет администратором. Для этого нужен **код установки**: сервер печатает его в логах при первом запуске с пустой базой.

```sh
docker compose logs app | grep "Код"
# [server] Пользователей ещё нет. Код для регистрации первого администратора: 3f9c1a7b2e44
```

Код защищает свежую установку: если адрес уже открыт наружу, посторонний не сможет зарегистрироваться первым и стать администратором. Код можно задать заранее в `.env` (`SETUP_CODE=...`).

Остальных пользователей администратор заводит в разделе **«Пользователи» → «+ Новый пользователь»**, или они регистрируются сами, если регистрация открыта (`REGISTRATION=open`, по умолчанию). Для доступа из интернета лучше `REGISTRATION=closed`.

### Шаг 6. Перенести данные из прошлой версии (необязательно)

Если файл `import/export.json` на месте:

```sh
docker compose exec app node scripts/import.js import/export.json
```

Импортируются пользователи, проекты и тест-кейсы. Старые пароли продолжат работать (при первом входе они автоматически перехэшируются в bcrypt). Повторный запуск безопасен: уже существующие записи пропускаются.

### Шаг 7. Автозапуск после перезагрузки

Контейнеры настроены с `restart: unless-stopped`: они поднимаются сами, когда запускается Docker.

- **Windows/macOS:** в Docker Desktop → Settings → General включите «Start Docker Desktop when you sign in». Настройте автоматический вход в учётную запись или не выходите из неё.
- **Linux:** `sudo systemctl enable docker`.
- **Везде:** отключите спящий режим (Windows: Параметры → Система → Питание; macOS: Настройки → Аккумулятор/Энергосбережение → «Не переходить в режим сна»). Пока компьютер спит, приложение недоступно.

### Шаг 8. Резервные копии

```sh
# Linux / macOS
./scripts/backup.sh
# Windows
powershell -ExecutionPolicy Bypass -File scripts\backup.ps1
```

В папке `backups/` появятся дамп базы и архив вложений, хранятся последние 14 копий. Чтобы делать это каждую ночь:

- **Linux/macOS:** `crontab -e` и строка `0 3 * * * cd /путь/к/testbol-qa && ./scripts/backup.sh`
- **Windows:** Планировщик заданий → Создать простую задачу → Ежедневно → Запуск программы `powershell`, аргументы `-ExecutionPolicy Bypass -File C:\testbol-qa\scripts\backup.ps1`.

Хорошо бы время от времени копировать папку `backups/` на другой диск или в облако.

Восстановление из копии:

```sh
gunzip -c backups/testbol-ГГГГ-ММ-ДД_ЧЧ-ММ.sql.gz | docker compose exec -T db psql -U testbed testbed
```

(на Windows: `Get-Content backups\файл.sql | docker compose exec -T db psql -U testbed testbed`). Восстанавливать лучше в пустую базу.

Вложения восстанавливаются отдельно:

```sh
# Linux / macOS
docker compose exec -T app tar -xzf - -C /app/data < backups/uploads-ГГГГ-ММ-ДД_ЧЧ-ММ.tar.gz
# Windows
docker compose cp backups\uploads-ГГГГ-ММ-ДД_ЧЧ-ММ\. app:/app/data/uploads
```

### Полезные команды

| Что сделать | Команда |
|---|---|
| Посмотреть логи | `docker compose logs -f app` |
| Остановить | `docker compose stop` |
| Запустить снова | `docker compose start` |
| Обновить после изменения кода | `git pull` и `docker compose up -d --build` |
| Зайти в базу через psql | `docker compose exec db psql -U testbed testbed` |
| Удалить всё **вместе с данными и вложениями** | `docker compose down -v` (осторожно!) |

### Разработка интерфейса

Интерфейс живёт в `web/` (React + TypeScript + Vite). В Docker он собирается автоматически. Для разработки с мгновенной перезагрузкой страницы:

```sh
docker compose up -d             # сервер и база
npm --prefix web install
npm run dev:web                  # http://localhost:5173, запросы /api уходят на localhost:3000
```

Чтобы собрать интерфейс без Docker (например, для `node server/index.js`), выполните `npm run build:web`: результат появится в `public/`.

## Часть 2. Доступ к приложению извне

Выберите один вариант в зависимости от того, откуда будут заходить коллеги.

По умолчанию приложение принимает соединения только с этого компьютера (`APP_BIND=127.0.0.1` в `.env`): туннели и прокси из вариантов Б и В обращаются к нему локально, а из сети напрямую его не видно.

### Вариант А. Только из локальной сети (офис, дом)

1. **Узнайте IP-адрес компьютера с приложением:**
   - Windows: `ipconfig` → «IPv4-адрес», например `192.168.1.50`
   - macOS: Настройки → Сеть → Wi-Fi/Ethernet → Подробнее
   - Linux: `hostname -I`
2. **Разрешите входящие подключения на порт 3000:**
   - Windows (PowerShell от имени администратора):
     ```powershell
     New-NetFirewallRule -DisplayName "TestBol QA" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow -Profile Private
     ```
     Сеть в Windows должна быть отмечена как «Частная».
   - Linux с ufw: `sudo ufw allow 3000/tcp`
   - macOS: при первом подключении система сама спросит разрешение.
3. **Закрепите IP за компьютером** в настройках роутера (раздел DHCP → «Резервирование адресов»), иначе после перезагрузки роутера адрес может смениться.
4. **Откройте приложение для сети** в `.env` и перезапустите (`docker compose up -d`):
   ```
   APP_BIND=0.0.0.0
   TRUST_PROXY=false
   ```
   `TRUST_PROXY=false` нужен, когда приложение открыто напрямую, без прокси: иначе любой в сети подделает свой IP в заголовке `X-Forwarded-For` и обойдёт ограничение попыток входа.
5. Коллеги открывают **http://192.168.1.50:3000** (подставьте свой адрес).

### Вариант Б. Из интернета через Tailscale — рекомендую для команды

Tailscale создаёт приватную зашифрованную сеть между вашими устройствами. Приложение видно только тем, кого вы пригласили, а порты на роутере открывать не нужно. Бесплатно до 3 пользователей и 100 устройств (условия проверьте на сайте).

1. Зарегистрируйтесь на [tailscale.com](https://tailscale.com) и установите Tailscale **на компьютер с приложением**. Войдите в аккаунт.
2. В [панели администратора](https://login.tailscale.com/admin/machines) найдите этот компьютер и для удобства отключите ему «Key expiry» (иначе раз в 180 дней нужно будет заново входить).
3. Пригласите коллег: Admin console → Users → Invite users. Каждый устанавливает Tailscale на свой компьютер или телефон и входит по приглашению.
4. На компьютере с приложением выполните
   ```sh
   tailscale serve --bg 3000
   ```
   Приложение будет доступно коллегам по HTTPS с нормальным сертификатом: `https://<имя-компьютера>.<ваш-tailnet>.ts.net` (точный адрес команда выведет). Возможно, сначала понадобится включить HTTPS в Admin console → DNS.

   Без `tailscale serve` коллеги могут открывать `http://<имя-компьютера>:3000` напрямую, но тогда, как в варианте А, задайте `APP_BIND=0.0.0.0` и `TRUST_PROXY=false`.

### Вариант В. Публичный адрес через Cloudflare Tunnel

Подходит, если нужен обычный адрес вроде `https://qa.example.com`, который открывается в любом браузере без установки программ. Понадобится свой домен, подключённый к Cloudflare (бесплатный тариф Cloudflare подходит; домен покупается отдельно).

1. Добавьте домен в [Cloudflare](https://dash.cloudflare.com) и смените у регистратора NS-серверы на те, что выдаст Cloudflare.
2. Откройте **Zero Trust** → **Networks** → **Tunnels** → **Create a tunnel** → тип **Cloudflared**. Назовите туннель, например `testbol`.
3. На шаге установки выберите Docker и скопируйте из показанной команды **токен** (длинная строка после `--token`). Вставьте его в `.env`:
   ```
   CLOUDFLARE_TUNNEL_TOKEN=eyJh...
   ```
4. На шаге **Public Hostname** укажите поддомен (`qa`) и домен, тип сервиса **HTTP**, URL **`app:3000`**.
5. Запустите туннель вместе с приложением:
   ```sh
   docker compose --profile tunnel up -d
   ```
6. Через минуту приложение откроется по адресу `https://qa.example.com`. Cloudflare сам выдаёт HTTPS-сертификат.
7. **Настоятельно рекомендую** закрыть адрес дополнительной проверкой: Zero Trust → **Access** → **Applications** → Add → Self-hosted, домен `qa.example.com`, политика Allow по списку email коллег. Тогда до страницы входа доберутся только они, а не весь интернет.

Названия пунктов в панели Cloudflare периодически меняются; если не находите нужный, ищите раздел «Tunnels» в Zero Trust.

### Чего лучше не делать

- **Не пробрасывайте порт 3000 на роутере** напрямую в интернет: соединение будет без HTTPS (пароли пойдут открытым текстом), а компьютер станет виден сканерам со всего мира. Tailscale и Cloudflare Tunnel решают задачу без этих рисков.
- Не открывайте наружу порт PostgreSQL (5432). В `docker-compose.yml` он намеренно не опубликован.

## Часть 3. Автотесты

Каждый запуск автотестов становится отдельной «папкой» во вкладке проекта **Автотесты**. В папке видно, что прошло, что упало, что сломалось или пропущено, текст ошибки, стектрейс, скриншоты и что было с тестом в прошлом запуске. Автотест заводится в реестре («Автотесты» → «Все автотесты») один раз, при первой встрече, и дальше узнаётся по набору и названию. Раздел тест-кейсов это не засоряет.

### Как подключить Playwright

1. Во вкладке «Автотесты» нажмите **Подключить автотесты** и создайте токен. Токен показывается один раз. Он годится только для отправки результатов: читать или менять баги и кейсы с ним нельзя. Каждому участнику лучше завести свой токен, тогда в запуске видно, кто его отправил.
2. Положите репортер рядом с `playwright.config` (его можно закоммитить):
   ```sh
   curl -o testbol-reporter.js http://localhost:3000/testbol-reporter.js
   ```
3. Добавьте его в `playwright.config`:
   ```js
   reporter: [["list"], ["./testbol-reporter.js"]],
   use: {
     screenshot: "only-on-failure",   // скриншот упавшего теста
     trace: "retain-on-failure",      // трейс упавшего теста (открывается на trace.playwright.dev)
   },
   ```
4. Задайте настройки и запускайте тесты как обычно:
   ```sh
   export TESTBOL_URL=http://localhost:3000
   export TESTBOL_TOKEN=tb_...
   export TESTBOL_PROJECT=LK
   npx playwright test
   ```
   В Windows PowerShell: `$env:TESTBOL_TOKEN="tb_..."`. Если переменные не заданы, репортер молча выключается: у коллег без токена и в CI без настроек тесты работают как обычно. Если TestBol недоступен, репортер пишет одно предупреждение и тесты не прерывает.

Необязательные переменные: `TESTBOL_TITLE` (название запуска, по умолчанию «Локальный запуск <ветка>»), `TESTBOL_ENV` (окружение, например `RC`), `TESTBOL_APP_URL` (адрес тестируемого приложения, по умолчанию `baseURL` из конфига), `TESTBOL_BUILD` (по умолчанию короткий хэш коммита), `TESTBOL_BRANCH`. Окружение и адрес можно передать и опциями репортера, взяв из своих переменных: `["./testbol-reporter.js", { appUrl: process.env.WEB_URL }]`.

В шапке запуска видно, что запускали (только проекты Playwright, которые реально выполнялись, с учётом `--project`), окружение и адрес приложения.

Шаги `test.step` уходят вместе с результатом, включая шаги из `beforeEach`. В результате видно, какие шаги прошли, сколько заняли и на каком тест упал; в списке запуска у упавшего теста написано «Упал на шаге: …», а «Завести баг» подставляет шаги в баг-репорт. В реестре («Все автотесты») у теста хранится список шагов из последнего прохождения.

Что попадает в папку запуска:

| Статус | Когда |
|---|---|
| Пройден | тест прошёл. Если со второй попытки (`retries`), рядом пометка «Нестабильный» |
| Упал | не прошла проверка `expect` |
| Сломан | таймаут теста или исключение в самом тесте |
| Пропущен | `test.skip` / `test.fixme`, а также тесты, до которых не дошла очередь (`--max-failures`, Ctrl+C) — с пометкой «Не выполнялся» |

Проекты Playwright (`chromium`, `mobile`…) считаются разными тестами: набор выглядит как `[mobile] login.spec.ts`. При повторах учитывается итоговая попытка, файлы прикладываются от неё же.

### Другие фреймворки: отчёт JUnit XML

pytest, Jest, Cypress, JUnit/TestNG и другие умеют писать отчёт JUnit XML. Его отправляет скрипт `report.js` (нужен Node.js 20+):

```sh
curl -O http://localhost:3000/report.js
node report.js results/junit.xml                                 # готовый отчёт
node report.js results/ -- pytest --junitxml=results/junit.xml   # запустить и отправить
```

С `--` скрипт сначала выполняет команду, затем отправляет только свежие отчёты и завершается с кодом самой команды. Настройки те же переменные `TESTBOL_*` или параметры `--url`, `--token`, `--project`, `--title`, `--build`, `--env`, `--branch`; справка — `node report.js --help`.

Скриншоты прикладываются к упавшим тестам, если отчёт ссылается на них строкой `[[ATTACHMENT|путь]]` в выводе теста или свойством `<property name="attachment" value="путь"/>`. Пути считаются от папки с отчётом или от текущей папки. Для pytest это делается в `conftest.py`:

```python
import os, pytest

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    rep = (yield).get_result()
    if rep.when == "call" and rep.failed:
        page = item.funcargs.get("page") or item.funcargs.get("driver")
        if page:
            os.makedirs("results/screenshots", exist_ok=True)
            path = f"results/screenshots/{item.name}.png"
            page.screenshot(path=path) if hasattr(page, "screenshot") else page.save_screenshot(path)
            item.user_properties.append(("attachment", path))  # попадёт в отчёт как <property name="attachment">
```

### Что важно знать

- Тест узнаётся по набору (`classname`) и названию. Переименованный тест заведётся как новый; старый можно удалить из реестра кнопкой ✕.
- Если тест встретился в отчёте дважды (перезапуск упавшего), в папке остаётся последний результат.
- Файлы больше `MAX_UPLOAD_MB` (по умолчанию 20 МБ) не прикладываются — обычно это длинные видео. Видео (`video: "retain-on-failure"`) прикладывается, если влезает.
- Своя интеграция без готовых скриптов: `POST /api/projects/<KEY>/autoruns` → `POST …/autoruns/<num>/results` (пачками до 1000) → скриншоты `POST …/results/<id>/attachments` → `PATCH …/autoruns/<num>` с `{"state":"finished"}`, всё с заголовком `Authorization: Bearer <токен>`. Все поля и примеры — в [docs/API.md](docs/API.md#автотесты).

## Часть 4. Локальная языковая модель (необязательно)

Небольшая модель работает на том же компьютере, что и TestBol: тексты багов и кейсов никуда не уходят. Без неё приложение работает как обычно.

**Требования.** Модель `qwen2.5:3b` занимает ~2 ГБ на диске и 3–4 ГБ памяти во время работы, хорошо понимает русский. Без видеокарты ответ идёт от 10 секунд до минуты. На слабом компьютере возьмите `qwen2.5:1.5b`, с видеокартой от 8 ГБ — `qwen2.5:7b`. В Docker Desktop проверьте, сколько памяти выдано WSL 2: модели нужно место сверх базы и приложения.

### Вариант А. Модель в Docker

1. В `.env`:
   ```
   LLM_URL=http://ollama:11434/v1
   LLM_MODEL=qwen2.5:3b
   ```
2. Запустите с профилем `llm`:
   ```sh
   docker compose --profile llm up -d
   ```
   При первом запуске `ollama-pull` скачивает модель. Следить: `docker compose logs -f ollama-pull`.
3. Проверьте: войдите в TestBol и откройте `http://localhost:3000/api/llm/status` — должно быть `"ready": true`.

Видеокарта NVIDIA: раскомментируйте блок `deploy` у сервиса `ollama` в `docker-compose.yml`.

### Вариант Б. Ollama прямо в системе

Быстрее на Windows и macOS: Ollama сама использует видеокарту (на Mac — Apple Silicon, которая из Docker недоступна).

1. Установите [Ollama](https://ollama.com/download) и скачайте модель: `ollama pull qwen2.5:3b`.
2. В `.env`: `LLM_URL=http://host.docker.internal:11434/v1`.
3. `docker compose up -d` (без профиля `llm`).

Вместо Ollama подойдёт любой сервер с OpenAI-совместимым API: llama.cpp (`llama-server`), LM Studio, vLLM. Укажите его адрес с `/v1` в `LLM_URL`, а в `LLM_MODEL` — имя модели так, как его показывает сервер.

### Где модель в интерфейсе

Отдельного раздела нет: кнопки «✨» появляются прямо в формах, когда модель готова.

| Где | Кнопка | Что делает |
|---|---|---|
| Новый баг / редактирование бага | ✨ Оформить с ИИ | Переписывает заметки в заголовок, шаги, фактический и ожидаемый результат, предлагает серьёзность |
| Новый тест-кейс / редактирование | ✨ Заполнить по названию | Предлагает предусловия, шаги и ожидаемый результат |
| Упавший автотест (карточка результата) | ✨ Объяснить падение | Кратко разбирает ошибку и стектрейс: что случилось, вероятная причина, что проверить |

После подстановки в форму можно нажать «Вернуть как было».

### Что важно знать

- Модель отвечает на один запрос за раз, остальные ждут в очереди (до 10). Когда очередь полна, пользователь видит «Модель занята».
- Ответ модели — подсказка: в базу он попадает только после того, как человек его проверил и сохранил.
- В логи пишется только число токенов и время ответа, сами тексты — нет.

## Безопасность в этой версии

- Роли: **тестировщик** работает со своими проектами (создаёт, меняет, удаляет), **разработчик** их просматривает и пишет комментарии, **администратор** видит все проекты и в разделе «Пользователи» меняет роли, блокирует и удаляет пользователей, выдаёт доступ к проектам. Проекты, в которые пользователя не добавили, для него не существуют. Права проверяет сервер на каждом запросе, интерфейс лишь прячет недоступные кнопки. Подробно — в [docs/API.md](docs/API.md#роли-и-доступ-к-проектам).
- Первый пользователь в пустой базе становится админом, но только с кодом установки из логов сервера (шаг 5). Дальше пользователей заводит админ или они регистрируются сами разработчиком без проектов (`REGISTRATION=open`); при `REGISTRATION=closed` зарегистрироваться самому нельзя. Если админа не осталось, задайте `ADMIN_LOGIN=<существующий логин>` в `.env` и перезапустите сервер; занять этот логин регистрацией нельзя.
- Новичок без проектов не видит ни других пользователей, ни администраторов.
- Пароли хранятся только в виде хэша bcrypt; участники их не видят. Хэширование идёт в отдельных потоках с ограниченной очередью: наплыв попыток входа или регистраций не останавливает сервер для остальных, а лишние запросы получают «Сервер перегружен».
- Свой пароль меняется кнопкой «Пароль» вверху страницы, админ сбрасывает пароль в «Пользователях». В обоих случаях остальные сессии пользователя закрываются.
- Сессия — случайный токен в cookie `HttpOnly`, `SameSite=Lax`; через HTTPS (Tailscale serve, Cloudflare) cookie называется `__Host-tb_session` и получает флаг `Secure`: такую cookie не может подставить соседний поддомен, например чужой туннель на том же домене провайдера. В базе лежит только хэш токена.
- Ограничение попыток: 10 неудачных входов за 15 минут на логин с одного адреса, 30 — с одного адреса на любые логины, 50 — на один логин с любых адресов (перебор пароля не обойти сменой IP); 5 регистраций в час с адреса и 30 в час всего.
- Изменяющие запросы принимаются только с `Content-Type: application/json`, это защищает от подделки запросов с чужих сайтов. Загрузка файлов требует отдельный заголовок `X-Upload`, который чужой сайт отправить не может.
- Страница приложения отдаётся с `Content-Security-Policy`: браузер выполняет только код самого приложения. Через HTTPS ставится `Strict-Transport-Security`. Шрифты лежат в сборке, сторонних запросов нет.
- Токены для автотестов хранятся только в виде хэша и умеют только отправлять результаты: создать запуск, прислать результаты и файлы, завершить запуск. Читать и удалять с ними нельзя ничего. Отзываются во вкладке «Автотесты» → «Подключить автотесты».
- Запросы к локальной модели ограничены: один одновременно и 20 за 10 минут на пользователя.
- Вложения доступны только вошедшим пользователям. В браузере открываются только картинки и текст, остальное отдаётся на скачивание, и всё под заголовком `Content-Security-Policy: sandbox`: загруженный HTML или SVG не выполнится. Размер файла ограничен `MAX_UPLOAD_MB` в `.env` (по умолчанию 20 МБ).

Что стоит добавить: журнал изменений (в том числе историю статусов бага и смены ролей).

**Про туннели на общем домене** (fxTunnel и подобные, адрес вида `*.fxtun.ru`): провайдер туннеля расшифровывает HTTPS у себя и видит пароли и cookie, а соседние туннели на том же домене браузер считает «тем же сайтом». Приложение защищено от подброшенных ими cookie, но для работы с настоящими данными надёжнее свой домен через Cloudflare Tunnel или Tailscale.

## Если что-то не работает

| Симптом | Что проверить |
|---|---|
| `docker: command not found` / `Cannot connect to the Docker daemon` | Docker Desktop не запущен или не установлен (шаг 1) |
| `Задайте POSTGRES_PASSWORD в файле .env` | Нет файла `.env` или в нём пустой пароль (шаг 3) |
| В логах `password authentication failed` | Пароль в `.env` поменяли после первого запуска. Верните прежний, либо, если данных ещё нет, `docker compose down -v` и запуск заново |
| `/api/llm/status` показывает `"ready": false` | `docker compose --profile llm ps`: запущен ли `ollama`; `docker compose logs ollama-pull`: скачалась ли модель; совпадает ли `LLM_MODEL` с `ollama list` |
| `port is already allocated` | Порт 3000 занят. Поменяйте `APP_PORT=3001` в `.env` и перезапустите |
| Коллеги из локальной сети не открывают страницу | `APP_BIND=0.0.0.0` в `.env` (вариант А, п. 4), брандмауэр (п. 2), правильный IP, оба устройства в одной сети |
| «Неверный код установки» при регистрации первого пользователя | Код в логах: `docker compose logs app`, строка «Код для регистрации первого администратора». Он печатается, только пока в базе нет ни одного пользователя |
| «Регистрация закрыта» | `REGISTRATION=closed`: учётную запись создаёт админ в разделе «Пользователи» |
| «Слишком много попыток» / «Сервер перегружен» | Сработала защита от перебора и наплыва запросов. Подождите 15 минут (при «перегружен» — минуту) |
| Страница открывается, но «Связь с сервером прервана» | Посмотрите `docker compose logs app`; при работе через прокси проверьте, что он не буферизует ответы |
