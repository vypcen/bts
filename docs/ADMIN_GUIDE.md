## Варианты установки

| Вариант | Когда подходит | Инструкция |
|---|---|---|
| **Docker Compose** на одном сервере | пилот, команда до 50–100 человек | [README, часть 1](../README.md#часть-1-развернуть-на-своём-компьютере) |
| **Kubernetes (Helm)** | корпоративная установка, несколько реплик, S3 для вложений | [README, часть 5](../README.md#kubernetes-helm) |

**Требования к серверу для пилота:** 2 ядра, 4 ГБ памяти, 20 ГБ диска плюс место под вложения; Docker 24+ или Kubernetes 1.25+; PostgreSQL 16 (в Compose поднимается сам). Доступ в интернет серверу не нужен: шрифты, справка и все библиотеки входят в образ.

Доступ пользователей: в локальной сети или через свой домен с HTTPS — [README, часть 2](../README.md#часть-2-доступ-к-приложению-извне). Для HTTPS задайте `PUBLIC_URL=https://…` и `TRUST_PROXY`, если перед приложением стоит прокси.

## Первый запуск

1. Запустите приложение и найдите в логе **код установки**: `docker compose logs app | grep "Код"`.
2. Откройте адрес приложения, зарегистрируйтесь с этим кодом — вы станете администратором.
3. Сразу решите, как появляются остальные пользователи:
   - `REGISTRATION=closed` — заводит только администратор (рекомендуется, если адрес доступен извне);
   - `REGISTRATION=open` — регистрируются сами и получают роль разработчика без проектов, доступ выдаёте вы;
   - SSO — см. ниже, пользователи создаются при первом входе.
4. Введите лицензионный ключ: **«Пользователи» → «Лицензия и система»**. Без ключа работает бесплатная редакция на 5 полных мест.
5. Создайте первый проект: **«Проекты» → «+ Новый проект»**, задайте короткий ключ (`LK`, `PAY`) — он войдёт в номера кейсов и багов.
6. Добавьте участников в проект и проверьте вход под тестировщиком.

Если администратор потерял доступ: задайте `ADMIN_LOGIN=<существующий логин>` в `.env` и перезапустите — этот пользователь станет администратором.

## Пользователи и роли

Раздел **«Пользователи»** (виден только администраторам).

| Роль | Права | Место в лицензии |
|---|---|---|
| Администратор | всё, плюс пользователи, доступы, лицензия, журнал аудита | полное |
| Тестировщик | создаёт, меняет и удаляет всё в своих проектах | полное |
| Разработчик | просмотр своих проектов, комментарии, статусы багов, помощник | просмотровое |
| Наблюдатель | только просмотр | просмотровое |

- **«+ Новый пользователь»** — логин, имя, временный пароль, роль.
- **«Изменить»** — общая роль и роли по проектам (тестировщик в одном, наблюдатель в другом), блокировка, сброс пароля. После сброса все сессии пользователя закрываются.
- **Заблокированный** пользователь не может войти, не занимает лицензию, но его действия в истории сохраняются. Блокируйте уволившихся, а не удаляйте.

### Свои роли

**«Пользователи» → «Роли»** — матрица: какие разрешения у каждой роли. Встроенные роли изменить нельзя; кнопка **«+ Роль»** создаёт свою с любым набором разрешений:

| Группа | Разрешения |
|---|---|
| Тест-кейсы | создавать и изменять кейсы, папки, импорт; удалять кейсы; вести требования |
| Прогоны | вести тест-планы; создавать, закрывать, удалять прогоны и распределять кейсы; отмечать результаты |
| Баги | заводить; изменять и связывать с трекером; менять статус; удалять |
| Общее | комментарии; помощник (языковая модель) |
| Автотесты | отправлять результаты, управлять автотестами, запускать CI |
| Проект | восстанавливать из корзины; настройки проекта (поля, трекер, вебхуки, CI); создавать и импортировать проекты (для глобальной роли) |

Примеры: **«Тест-менеджер»** — планы, прогоны, требования, комментарии (без правки кейсов); **«Автоматизатор»** — автотесты, кейсы, заводить баги; **«Аналитик заказчика»** — только комментарии.

Своя роль выдаётся так же, как встроенная: глобально («Пользователи», колонка «Роль») или в конкретном проекте («Изменить» в колонке проектов). Просматривать проект может любой его участник, разрешения нужны только для изменений. Сервер проверяет разрешение на каждый запрос; кнопки, недоступные роли, в интерфейсе скрыты.

**Лицензия.** Роль, в которой есть только «комментарии», «менять статус бага» и «помощник», занимает просмотровое место; любое другое разрешение — полное. Полное место занимает пользователь, у которого полная роль глобально **или хотя бы в одном проекте**. Если изменение роли потребует больше полных мест, чем есть в лицензии, сохранить его не получится.

Удалить роль, которая кому-то выдана, можно только указав, какую роль выдать вместо неё. Создание, изменение и удаление ролей пишутся в журнал аудита.

## Проекты и доступ

- Пользователь видит только проекты, в которые его добавили. Администратор видит все.
- Тестировщики проекта управляют его настройками (вкладка «Настройки»): трекер, CI, вебхуки, пользовательские поля.
- **Удалить проект** может только администратор, введя ключ проекта для подтверждения. Удалённый проект 30 дней хранится в **«Пользователи» → «Удалённые проекты»** и восстанавливается целиком; там же его можно удалить окончательно.

## Политики паролей и сессий, двухфакторная аутентификация

Задаются переменными окружения (в Helm — в `env`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `TWO_FACTOR` | `optional` | `optional` — каждый включает 2FA по желанию; `required` — обязательна всем, кто входит по паролю (в том числе через LDAP); `admins` — обязательна администраторам; `off` — выключена |
| `PASSWORD_MIN_LENGTH` | 8 | минимальная длина пароля (рекомендуем 10–12) |
| `PASSWORD_MIN_CLASSES` | 2 | сколько видов символов из четырёх (строчные, прописные, цифры, знаки) должно быть в пароле |
| `PASSWORD_MAX_AGE_DAYS` | 0 | через сколько дней пароль нужно сменить (0 — бессрочно) |
| `PASSWORD_HISTORY` | 0 | сколько последних паролей нельзя повторять |
| `PASSWORD_CHANGE_ON_RESET` | `true` | пароль, выданный администратором, пользователь меняет при первом входе |
| `SESSION_DAYS` | 30 | максимальный срок сессии |
| `SESSION_IDLE_MINUTES` | 0 | закрывать сессию после стольких минут без действий (0 — не закрывать) |
| `MAX_SESSIONS` | 0 | сколько одновременных сессий у пользователя; при новом входе самая старая закрывается (0 — без ограничения) |
| `TOTP_ISSUER` | `TestBall` | название системы в приложении-аутентификаторе |

Популярные пароли (`password123`, `qwerty123`, `12345678` и т. п.) и пароль, содержащий логин, не принимаются никогда.

**Двухфакторная аутентификация** — по стандарту TOTP: подходит любое приложение-аутентификатор (Яндекс Ключ, Google Authenticator, Microsoft Authenticator, менеджеры паролей). Пользователь включает её в «Безопасность» вверху страницы и получает 10 одноразовых резервных кодов. Секрет хранится в базе зашифрованным ключом `APP_SECRET`. Если 2FA обязательна, после входа пользователь сначала её настраивает, а сервер до этого не отдаёт данные. Пользователи OIDC и Kerberos проходят второй фактор в своём IdP — к ним требование не относится.

**Если сотрудник потерял телефон:** «Пользователи» → **«Сбросить 2FA»**. Он войдёт по паролю и (если 2FA обязательна) настроит её заново.

**Сессии:** в «Пользователях» видно, у кого сколько активных сессий; **«Завершить сессии»** выкидывает пользователя на всех устройствах (потерян ноутбук). Пользователь видит свои сессии в «Безопасность» → «Активные сессии».

Включение и отключение 2FA, сброс, вход по резервному коду, неверные коды и завершение сессий записываются в журнал аудита.

## Единый вход (SSO)

Поддерживаются **OpenID Connect** (Keycloak, ADFS, Entra ID, Okta и другие поставщики с OIDC), **LDAP / Active Directory** и **Kerberos** через доверенный прокси.

Роли назначаются по группам каталога: `SSO_ADMIN_GROUPS`, `SSO_TESTER_GROUPS`, `SSO_DEVELOPER_GROUPS`, `SSO_VIEWER_GROUPS`; `SSO_DEFAULT_ROLE` — роль, если ни одна группа не подошла; `SSO_REQUIRED_GROUPS` — пускать только участников этих групп; `SSO_PROJECT_GROUP_RE` — выдавать доступ к проектам по названию группы (с выражением `^TB-([A-Z]{2,6})(?:-(tester|developer|viewer))?$` группа `TB-LK-tester` даёт роль тестировщика в проекте `LK`). Роль пересчитывается при каждом входе.

`LOCAL_LOGIN=false` отключает вход по паролю (останется только SSO). Перед этим убедитесь, что хотя бы один администратор входит через SSO.

Настройка по шагам и примеры для каждого провайдера — [README, «Единый вход»](../README.md#единый-вход-openid-connect-ldap--ad-kerberos).

## Лицензия

**«Пользователи» → «Лицензия и система»**: редакция, владелец, срок, занятые места; кнопка **«Ввести ключ»**. Ключ можно задать и переменной `LICENSE_KEY` (в Helm — `secrets.licenseKey`); введённый в интерфейсе главнее.

- Полные места — администраторы и тестировщики; просмотровые — разработчики и наблюдатели. Заблокированные не считаются.
- Когда места кончились, нельзя выдать новую полную роль; работающих пользователей это не затрагивает. Новые пользователи из SSO в этом случае получают роль наблюдателя.
- За 30 дней до окончания лицензии администратор видит предупреждение вверху страницы. После окончания 14 дней всё работает как прежде, затем — лимиты бесплатной редакции. Данные никогда не блокируются.
- Ключ может быть привязан к адресу (`PUBLIC_URL`): при переезде на другой адрес запросите у поставщика новый ключ.

## Настройки проекта: трекеры, CI, вебхуки, поля

Вкладка проекта **«Настройки»** (тестировщики и администраторы):

- **Трекер задач** — Jira, YouTrack, GitLab, GitHub, Redmine: создание задачи из бага, автосоздание для новых багов, перевод бага в «Исправлен», когда задачу закрыли.
- **Задачи CI** — GitLab CI, GitHub Actions, Jenkins или любой адрес, принимающий запрос на запуск: кнопка «Запустить в CI» на вкладке «Автотесты» с параметрами (ветка, окружение, адрес приложения).
- **Вебхуки** — уведомления в мессенджеры и свои системы о событиях (баг создан, прогон завершён и т. п.) с шаблоном тела запроса и условиями. `WEBHOOK_BLOCK_PRIVATE=true` запрещает адреса во внутренней сети.
- **Пользовательские поля** — для кейсов, багов и прогонов: текст, число, список, дата, флажок, пользователь; можно сделать обязательными.
- **Языковая модель** — подключает администратор кнопкой **«Настройки»** вверху страницы (это общая настройка, не проекта): GigaChat, YandexGPT, Anthropic или любая OpenAI-совместимая модель, в том числе развёрнутая в своём контуре (vLLM, Ollama); `LLM_ALLOW_CLOUD=false` запрещает отправку текстов во внешние сервисы. Подробно — [README, часть 4](../README.md#часть-4-языковая-модель-необязательно).

Секреты интеграций хранятся в базе зашифрованными ключом из `APP_SECRET`. **Не теряйте `APP_SECRET`**: без него сохранённые токены трекеров и CI придётся ввести заново.

## Токены и API

Токены создаются на вкладке **«Автотесты» → «Подключить автотесты»**. Права токена:

- **«Результаты автотестов»** — только отправка результатов из CI (по умолчанию). Даже утёкший такой токен не даст прочитать или удалить данные.
- **«API: чтение»** — для отчётов, BI, интеграций.
- **«API: чтение и запись»** — для синхронизации с другими системами.

Токен не даёт больше прав, чем у его владельца, может быть ограничен одним проектом и сроком действия. Управлять пользователями и токенами через токен нельзя. Описание API — [docs/API.md](API.md); интеграциям рекомендуем пути `/api/v1/…`.

Для CI заведите отдельного пользователя-«робота» с ролью тестировщика только в нужных проектах и создайте токены от его имени: так токены не пропадут при уходе сотрудника.

## Журнал аудита и корзина

- **«Пользователи» → «Журнал аудита»**: входы и неудачные попытки, роли и доступы, лицензия, удаления и восстановления, интеграции, токены, выгрузки. Фильтры по пользователю, действию, проекту и дате, выгрузка в CSV. Хранится `AUDIT_RETENTION_DAYS` дней (по умолчанию 365).
- **Корзина проекта**: удалённые кейсы, прогоны и баги `TRASH_DAYS` дней (по умолчанию 30). Восстанавливают тестировщики проекта; окончательно удаляет администратор.

## Резервное копирование и восстановление

**Docker Compose:** `./scripts/backup.sh` (Windows — `scripts\backup.ps1`) — копия базы и вложений в `backups/`. Поставьте в расписание (cron, Планировщик заданий) и копируйте папку на другой сервер. Восстановление — [README, шаг 8](../README.md#шаг-8-резервные-копии).

**Kubernetes:** снимки PostgreSQL средствами вашего кластера (pg_dump, WAL-архивирование) и версионирование бакета S3 для вложений.

Что обязательно сохранить вне сервера: резервные копии, файл `.env` (в нём `APP_SECRET` и `POSTGRES_PASSWORD`), лицензионный ключ.

Проверяйте восстановление хотя бы раз в квартал на отдельном стенде: копия, из которой ни разу не восстанавливались, — не копия.

## Обновление

Порядок, откат и выпуск версий — [docs/UPGRADE.md](UPGRADE.md), изменения версий — [CHANGELOG](../CHANGELOG.md). Коротко: резервная копия → новая версия → проверка на странице «Лицензия и система». ## Мониторинг

### Проверки состояния

- `GET /livez` — процесс жив (liveness-проверка Kubernetes).
- `GET /readyz` — сервер готов принимать запросы: запуск и миграции закончены, база доступна (readiness-проверка, балансировщик). Во время остановки отвечает `503`, чтобы балансировщик снял трафик заранее.
- `GET /healthz` — база доступна (проверка в Docker Compose).

### Журнал работы

Журнал пишется в stdout контейнера: `docker compose logs app`, `kubectl logs`.

- `LOG_FORMAT=json` — по строке JSON на событие: `{"ts","level","component","msg",…}`. Подходит для Loki, ELK, Graylog, Vector без разбора регулярными выражениями. В Helm включён по умолчанию.
- `LOG_LEVEL` — `debug`, `info` (по умолчанию), `warn`, `error`.
- **Журнал запросов** (`LOG_REQUESTS=true`, в режиме json включён сам): метод, путь, код ответа, время, пользователь, IP и номер запроса. Проверки состояния и поток живых обновлений не пишутся.
- **Номер запроса.** У каждого запроса есть номер: заголовок ответа `X-Request-Id` (если номер уже поставил ваш прокси, используется он). При внутренней ошибке пользователь видит «Код запроса для поддержки: 3f9c1a7b2e44» — по этому коду в журнале находится запись с путём, пользователем и стеком ошибки.
- **Медленные запросы к базе** (дольше `SLOW_QUERY_MS`, по умолчанию 1000 мс) пишутся с `component=db` и текстом запроса.
- Поле `component` показывает источник: `server`, `http`, `db`, `migrate`, `trackers`, `webhooks`, `ci`, `sso`, `audit` и т. д.

### Метрики Prometheus

Задайте `METRICS_TOKEN` (длинная случайная строка) — появится `GET /metrics` с заголовком `Authorization: Bearer <токен>`. Без токена эндпоинт выключен, чтобы метрики не оказались снаружи за обратным прокси.

| Метрика | Что показывает |
|---|---|
| `testball_http_requests_total{method,route,status}` | запросы по маршрутам и кодам ответа |
| `testball_http_request_duration_seconds` | время ответа (гистограмма) по маршрутам |
| `testball_db_query_duration_seconds`, `testball_db_query_errors_total` | время и ошибки запросов к PostgreSQL |
| `testball_db_pool_connections{state}` | соединения пула: всего, свободные, ожидающие |
| `testball_live_clients` | открытые вкладки с живыми обновлениями |
| `testball_users{state}`, `testball_projects`, `testball_sessions` | пользователи, проекты, сессии |
| `testball_webhook_failed_last_hour` | неудачные доставки вебхуков за час |
| `testball_log_errors_total{level,component}` | ошибки и предупреждения в журнале |
| `testball_info{version,commit}` | версия и сборка |
| `testball_process_*`, `testball_nodejs_*` | память, процессор, задержка цикла событий, сборка мусора |

В Kubernetes: `secrets.metricsToken` и `metrics.serviceMonitor.enabled=true` (нужен Prometheus Operator). Готовый **дашборд Grafana** и **правила оповещений** (сервис недоступен, больше 2% ошибок, медленные ответы, нехватка соединений с базой, память, перегрузка, недоставленные вебхуки) — в папке `deploy/monitoring/`.

### Фоновые задачи

Доставка вебхуков, создание задач в трекере, синхронизация статусов с трекером, удаление устаревших данных и файлов идут через **очередь задач в PostgreSQL**:

- задачи переживают перезапуск: вебхук, который не успел уйти, доставится после старта;
- при ошибке задача повторяется с нарастающей паузой (вебхуки — `WEBHOOK_RETRIES`, по умолчанию через 5 с, 30 с, 5 мин и 30 мин); ошибка настройки (ответ 4xx) не повторяется;
- при нескольких репликах каждую задачу выполняет одна реплика, периодические задачи тоже запускаются на одной;
- если реплика упала посреди задачи, задачу через несколько минут подхватит другая.

**«Пользователи» → «Лицензия и система» → «Фоновые задачи»**: сколько задач в очереди и выполнено за сутки, упавшие задачи с текстом ошибки и кнопкой «Повторить». Метрики `testball_jobs{status}` и `testball_jobs_lag_seconds`, оповещение `TestBallJobsStuck`.

Настройки: `JOB_CONCURRENCY` — сколько задач одна реплика выполняет одновременно (4), `JOB_POLL_MS` — как часто проверять очередь (1000 мс).

### Страница «Лицензия и система»

Лицензия, версия, сборка, версия PostgreSQL, число миграций и история обновлений, фоновые задачи; кнопка «Скопировать для поддержки».

## Перенос данных из других систем

- **Из TestRail, TestLink, Qase:** «Проекты» → **«Импорт»** → источник и файл выгрузки (TestRail — XML, TestLink — XML, Qase — JSON). Разделы станут папками, шаги с ожидаемыми результатами — шагами кейсов. Перед созданием проекта видно, сколько будет перенесено.
- **Из другой установки TestBall:** вкладка проекта «Настройки» → **«Скачать со всеми вложениями»** (или без вложений) — JSON со всем проектом. Загрузка: «Проекты» → «Импорт» → «TestBall», с новым ключом.
- **Кейсы из Excel/CSV** — во вкладке «Тест-кейсы» → «Импорт» (понимает выгрузки TestRail и Qase).
- **Требования** — из CSV или выгрузки Jira во вкладке «Требования» → «Импорт».

Размер загружаемого файла ограничен `IMPORT_MAX_MB`.

## Персональные данные (152-ФЗ)

Какие персональные данные хранит система, сколько и как выполнять запросы субъектов — в отдельном документе [«Персональные данные»](PERSONAL_DATA.md). Коротко:

- `PRIVACY_POLICY_URL` — ссылка на вашу политику обработки ПДн на странице входа и обязательное согласие при самостоятельной регистрации;
- **«Пользователи» → «Данные (152-ФЗ)»** — выгрузка всех данных пользователя одним файлом;
- **«Пользователи» → «Обезличить»** — при отзыве согласия или по регламенту после увольнения: личные данные удаляются, история работы остаётся;
- IP-адреса в журнале аудита стираются через `AUDIT_IP_DAYS` дней (180).

## Рекомендации по безопасности

1. Работайте по HTTPS (`PUBLIC_URL=https://…`), закройте прямой доступ к порту приложения и базы.
2. `REGISTRATION=closed` или вход только через SSO (`LOCAL_LOGIN=false`).
3. Двухфакторная аутентификация хотя бы для администраторов: `TWO_FACTOR=admins` (лучше — `required`), `PASSWORD_MIN_LENGTH=10`, `SESSION_IDLE_MINUTES=480`.
4. Длинные случайные `POSTGRES_PASSWORD` и `APP_SECRET`; храните `.env` с правами только для администратора.
5. Блокируйте уволившихся в день увольнения (с SSO это происходит само при отключении в каталоге).
6. Токены для CI — от пользователя-робота, с правом «Результаты автотестов» и ограничением проектом.
7. Раз в месяц просматривайте журнал аудита: неудачные входы, выдачу ролей администратора, удаления.
8. Обновляйтесь на патч-версии: в них исправления, в том числе уязвимостей.

Подробно о встроенных защитах — [README, «Безопасность»](../README.md#безопасность-в-этой-версии).

## Обращение в поддержку

Приложите к обращению:

1. Текст с кнопки **«Скопировать для поддержки»** («Пользователи» → «Лицензия и система»): версия, сборка, PostgreSQL, миграции.

3. Код запроса из сообщения об ошибке, если он был («Код запроса для поддержки: …»).
4. Логи за это время: `docker compose logs --since 1h app > testball.log`.

Не присылайте `.env`, резервные копии и токены.
