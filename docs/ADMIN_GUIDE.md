## Варианты установки

| Вариант | Когда подходит | Инструкция |
|---|---|---|
| **Docker Compose** на одном сервере | пилот, команда до 50–100 человек | [README, часть 1](../README.md#часть-1-развернуть-на-своём-компьютере) |
| **Kubernetes (Helm)** | корпоративная установка, несколько реплик, S3 для вложений | [README, часть 5](../README.md#kubernetes-helm) |

**Требования к серверу для пилота:** 2 ядра, 4 ГБ памяти, 20 ГБ диска плюс место под вложения; Docker 24+ или Kubernetes 1.25+; PostgreSQL 16 (в Compose поднимается сам). Доступ в интернет серверу не нужен: шрифты, справка и все библиотеки входят в образ.

Доступ пользователей: в локальной сети или через свой домен с HTTPS — [README, часть 2](../README.md#часть-2-доступ-к-приложению-извне). Для HTTPS задайте `PUBLIC_URL=https://…` и `TRUST_PROXY`, если перед приложением стоит прокси.

## Первый запуск

1. Запустите приложение и найдите в логе **код установки**: `docker compose logs app | grep "Код"`.
2. Откройте адрес приложения, зарегистрируйтесь с этим кодом — вы станете администратором.
3. Сразу решите, как появляются остальные пользователи:
   - `REGISTRATION=closed` — заводит только администратор (рекомендуется, если адрес доступен извне);
   - `REGISTRATION=open` — регистрируются сами и получают роль разработчика без проектов, доступ выдаёте вы;
   - SSO — см. ниже, пользователи создаются при первом входе.
4. Введите лицензионный ключ: **«Пользователи» → «Лицензия и система»**. Без ключа работает бесплатная редакция на 5 полных мест.
5. Создайте первый проект: **«Проекты» → «+ Новый проект»**, задайте короткий ключ (`LK`, `PAY`) — он войдёт в номера кейсов и багов.
6. Добавьте участников в проект и проверьте вход под тестировщиком.

Если администратор потерял доступ: задайте `ADMIN_LOGIN=<существующий логин>` в `.env` и перезапустите — этот пользователь станет администратором.

## Пользователи и роли

Раздел **«Пользователи»** (виден только администраторам).

| Роль | Права | Место в лицензии |
|---|---|---|
| Администратор | всё, плюс пользователи, доступы, лицензия, журнал аудита | полное |
| Тестировщик | создаёт, меняет и удаляет всё в своих проектах | полное |
| Разработчик | просмотр своих проектов, комментарии, статусы багов | просмотровое |
| Наблюдатель | только просмотр | просмотровое |

- **«+ Новый пользователь»** — логин, имя, временный пароль, роль.
- **«Изменить»** — общая роль и роли по проектам (тестировщик в одном, наблюдатель в другом), блокировка, сброс пароля. После сброса все сессии пользователя закрываются.
- **Заблокированный** пользователь не может войти, не занимает лицензию, но его действия в истории сохраняются. Блокируйте уволившихся, а не удаляйте.
- Права проверяет сервер на каждом запросе; интерфейс лишь прячет недоступные кнопки.

## Проекты и доступ

- Пользователь видит только проекты, в которые его добавили. Администратор видит все.
- Тестировщики проекта управляют его настройками (вкладка «Настройки»): трекер, CI, вебхуки, пользовательские поля.
- **Удалить проект** может только администратор, введя ключ проекта для подтверждения. Удалённый проект 30 дней хранится в **«Пользователи» → «Удалённые проекты»** и восстанавливается целиком; там же его можно удалить окончательно.

## Единый вход (SSO)

Поддерживаются **OpenID Connect** (Keycloak, ADFS, Entra ID, Okta и другие поставщики с OIDC), **LDAP / Active Directory** и **Kerberos** через доверенный прокси.

Роли назначаются по группам каталога: `SSO_ADMIN_GROUPS`, `SSO_TESTER_GROUPS`, `SSO_DEVELOPER_GROUPS`, `SSO_VIEWER_GROUPS`; `SSO_DEFAULT_ROLE` — роль, если ни одна группа не подошла; `SSO_REQUIRED_GROUPS` — пускать только участников этих групп; `SSO_PROJECT_GROUP_RE` — выдавать доступ к проектам по названию группы (с выражением `^TB-([A-Z]{2,6})(?:-(tester|developer|viewer))?$` группа `TB-LK-tester` даёт роль тестировщика в проекте `LK`). Роль пересчитывается при каждом входе.

`LOCAL_LOGIN=false` отключает вход по паролю (останется только SSO). Перед этим убедитесь, что хотя бы один администратор входит через SSO.

Настройка по шагам и примеры для каждого провайдера — [README, «Единый вход»](../README.md#единый-вход-openid-connect-ldap--ad-kerberos).

## Лицензия

**«Пользователи» → «Лицензия и система»**: редакция, владелец, срок, занятые места; кнопка **«Ввести ключ»**. Ключ можно задать и переменной `LICENSE_KEY` (в Helm — `secrets.licenseKey`); введённый в интерфейсе главнее.

- Полные места — администраторы и тестировщики; просмотровые — разработчики и наблюдатели. Заблокированные не считаются.
- Когда места кончились, нельзя выдать новую полную роль; работающих пользователей это не затрагивает. Новые пользователи из SSO в этом случае получают роль наблюдателя.
- За 30 дней до окончания лицензии администратор видит предупреждение вверху страницы. После окончания 14 дней всё работает как прежде, затем — лимиты бесплатной редакции. Данные никогда не блокируются.
- Ключ может быть привязан к адресу (`PUBLIC_URL`): при переезде на другой адрес запросите у поставщика новый ключ.

## Настройки проекта: трекеры, CI, вебхуки, поля

Вкладка проекта **«Настройки»** (тестировщики и администраторы):

- **Трекер задач** — Jira, YouTrack, GitLab, GitHub, Redmine: создание задачи из бага, автосоздание для новых багов, перевод бага в «Исправлен», когда задачу закрыли.
- **Задачи CI** — GitLab CI, GitHub Actions, Jenkins или любой адрес, принимающий запрос на запуск: кнопка «Запустить в CI» на вкладке «Автотесты» с параметрами (ветка, окружение, адрес приложения).
- **Вебхуки** — уведомления в мессенджеры и свои системы о событиях (баг создан, прогон завершён и т. п.) с шаблоном тела запроса и условиями. `WEBHOOK_BLOCK_PRIVATE=true` запрещает адреса во внутренней сети.
- **Пользовательские поля** — для кейсов, багов и прогонов: текст, число, список, дата, флажок, пользователь; можно сделать обязательными.
- **Языковая модель** — подключает администратор кнопкой **«Настройки»** вверху страницы (это общая настройка, не проекта): GigaChat, YandexGPT, Anthropic или любая OpenAI-совместимая модель, в том числе развёрнутая в своём контуре (vLLM, Ollama); `LLM_ALLOW_CLOUD=false` запрещает отправку текстов во внешние сервисы. Подробно — [README, часть 4](../README.md#часть-4-языковая-модель-необязательно).

Секреты интеграций хранятся в базе зашифрованными ключом из `APP_SECRET`. **Не теряйте `APP_SECRET`**: без него сохранённые токены трекеров и CI придётся ввести заново.

## Токены и API

Токены создаются на вкладке **«Автотесты» → «Подключить автотесты»**. Права токена:

- **«Результаты автотестов»** — только отправка результатов из CI (по умолчанию). Даже утёкший такой токен не даст прочитать или удалить данные.
- **«API: чтение»** — для отчётов, BI, интеграций.
- **«API: чтение и запись»** — для синхронизации с другими системами.

Токен не даёт больше прав, чем у его владельца, может быть ограничен одним проектом и сроком действия. Управлять пользователями и токенами через токен нельзя. Описание API — [docs/API.md](API.md); интеграциям рекомендуем пути `/api/v1/…`.

Для CI заведите отдельного пользователя-«робота» с ролью тестировщика только в нужных проектах и создайте токены от его имени: так токены не пропадут при уходе сотрудника.

## Журнал аудита и корзина

- **«Пользователи» → «Журнал аудита»**: входы и неудачные попытки, роли и доступы, лицензия, удаления и восстановления, интеграции, токены, выгрузки. Фильтры по пользователю, действию, проекту и дате, выгрузка в CSV. Хранится `AUDIT_RETENTION_DAYS` дней (по умолчанию 365).
- **Корзина проекта**: удалённые кейсы, прогоны и баги `TRASH_DAYS` дней (по умолчанию 30). Восстанавливают тестировщики проекта; окончательно удаляет администратор.

## Резервное копирование и восстановление

**Docker Compose:** `./scripts/backup.sh` (Windows — `scripts\backup.ps1`) — копия базы и вложений в `backups/`. Поставьте в расписание (cron, Планировщик заданий) и копируйте папку на другой сервер. Восстановление — [README, шаг 8](../README.md#шаг-8-резервные-копии).

**Kubernetes:** снимки PostgreSQL средствами вашего кластера (pg_dump, WAL-архивирование) и версионирование бакета S3 для вложений.

Что обязательно сохранить вне сервера: резервные копии, файл `.env` (в нём `APP_SECRET` и `POSTGRES_PASSWORD`), лицензионный ключ.

Проверяйте восстановление хотя бы раз в квартал на отдельном стенде: копия, из которой ни разу не восстанавливались, — не копия.

## Обновление

Порядок, откат и выпуск версий — [docs/UPGRADE.md](UPGRADE.md), изменения версий — [CHANGELOG](../CHANGELOG.md). Коротко: резервная копия → новая версия → проверка на странице «Лицензия и система». Миграции базы применяются сами. Запустить старую версию на обновлённой базе сервер не даст — откат только из резервной копии.

## Мониторинг

- `GET /livez` — процесс жив (liveness-проверка Kubernetes).
- `GET /readyz` — сервер готов принимать запросы: запуск и миграции закончены, база доступна (readiness-проверка, балансировщик). Во время остановки отвечает `503`, чтобы балансировщик снял трафик заранее.
- `GET /healthz` — база доступна (проверка в Docker Compose).
- Логи — в stdout контейнера: `docker compose logs app`, `kubectl logs`. Ошибки помечены `[server]`, `[migrate]`, `[trackers]`, `[webhooks]` и т. п.
- На странице «Лицензия и система» — версия, сборка, версия PostgreSQL, число миграций и история обновлений; кнопка «Скопировать для поддержки».

## Перенос данных из других систем

- **Из TestRail, TestLink, Qase:** «Проекты» → **«Импорт»** → источник и файл выгрузки (TestRail — XML, TestLink — XML, Qase — JSON). Разделы станут папками, шаги с ожидаемыми результатами — шагами кейсов. Перед созданием проекта видно, сколько будет перенесено.
- **Из другой установки TestBall:** вкладка проекта «Настройки» → **«Скачать со всеми вложениями»** (или без вложений) — JSON со всем проектом. Загрузка: «Проекты» → «Импорт» → «TestBall», с новым ключом.
- **Кейсы из Excel/CSV** — во вкладке «Тест-кейсы» → «Импорт» (понимает выгрузки TestRail и Qase).
- **Требования** — из CSV или выгрузки Jira во вкладке «Требования» → «Импорт».

Размер загружаемого файла ограничен `IMPORT_MAX_MB`.

## Рекомендации по безопасности

1. Работайте по HTTPS (`PUBLIC_URL=https://…`), закройте прямой доступ к порту приложения и базы.
2. `REGISTRATION=closed` или вход только через SSO (`LOCAL_LOGIN=false`).
3. Длинные случайные `POSTGRES_PASSWORD` и `APP_SECRET`; храните `.env` с правами только для администратора.
4. Блокируйте уволившихся в день увольнения (с SSO это происходит само при отключении в каталоге).
5. Токены для CI — от пользователя-робота, с правом «Результаты автотестов» и ограничением проектом.
6. Раз в месяц просматривайте журнал аудита: неудачные входы, выдачу ролей администратора, удаления.
7. Обновляйтесь на патч-версии: в них исправления, в том числе уязвимостей.

Подробно о встроенных защитах — [README, «Безопасность»](../README.md#безопасность-в-этой-версии).

## Справочник настроек

Все переменные с пояснениями — в файле [`.env.example`](../.env.example). Основные:

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | пароль базы (обязательно) |
| `APP_SECRET` | ключ шифрования секретов интеграций; не менять после запуска |
| `PUBLIC_URL` | внешний адрес приложения (ссылки в письмах, вебхуках, SSO, привязка лицензии) |
| `APP_PORT`, `APP_BIND` | порт и интерфейс (`0.0.0.0` — доступ из локальной сети) |
| `TRUST_PROXY` | приложение за обратным прокси |
| `REGISTRATION` | `open` / `closed` |
| `LOCAL_LOGIN` | вход по паролю (`false` — только SSO) |
| `LICENSE_KEY` | лицензионный ключ |
| `MAX_UPLOAD_MB`, `IMPORT_MAX_MB` | размер вложения и файла импорта |
| `STORAGE`, `S3_*` | где хранить вложения: `local` (диск) или `s3` |
| `TRASH_DAYS`, `AUDIT_RETENTION_DAYS` | срок хранения корзины и журнала аудита |
| `TOKEN_RATE_LIMIT` | запросов в минуту с одного API-токена |
| `REPORT_COMPANY` | название компании в шапке PDF-отчётов |
| `LDAP_*`, `OIDC_*`, `KERBEROS_*`, `SSO_*` | единый вход |
| `LLM_*` | языковая модель |
| `FLAKY_*` | как определяются нестабильные автотесты |

## Обращение в поддержку

Приложите к обращению:

1. Текст с кнопки **«Скопировать для поддержки»** («Пользователи» → «Лицензия и система»): версия, сборка, PostgreSQL, миграции.
2. Что делали, что ожидали, что произошло; время события.
3. Логи за это время: `docker compose logs --since 1h app > testball.log`.

Не присылайте `.env`, резервные копии и токены.
