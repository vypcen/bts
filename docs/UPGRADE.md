# Обновление TestBall QA

Коротко: **сделайте резервную копию → поставьте новую версию → проверьте «О системе»**. Миграции базы применяются сами при запуске.

## Перед обновлением

1. Прочитайте раздел новой версии в [CHANGELOG.md](../CHANGELOG.md): что изменилось и нужно ли что-то сделать заранее. Перед мажорной версией (2.0, 3.0) — обязательно.
2. Узнайте текущую версию: «Пользователи → О системе» (только администратор) или строка `TestBall QA X.Y.Z запущен` в логе.
3. **Сделайте резервную копию базы и вложений.** Без неё откатиться назад нельзя: старая версия не запустится на обновлённой базе.
   - Из интерфейса: «Пользователи → Резервные копии» → «Создать сейчас», дождитесь «✓ пройдена».
   - Docker Compose: `./scripts/backup.sh` (Windows: `scripts\backup.ps1`), копия появится в `backups/`.
   - Kubernetes: снимок или `pg_dump` базы средствами вашего кластера PostgreSQL; вложения в S3 — версионирование бакета или копия.

## Docker Compose

```sh
./scripts/backup.sh
git fetch --tags && git checkout v1.1.0      # или git pull, если вы на ветке main
docker compose up -d --build
docker compose logs -f app                   # ждём «[migrate] применена …» и «запущен»
```

## Kubernetes (Helm)

```sh
docker build --build-arg BUILD_COMMIT=$(git rev-parse HEAD) --build-arg BUILD_DATE=$(date -u +%FT%TZ) \
  -t registry.company.ru/qa/testball:1.1.0 . && docker push registry.company.ru/qa/testball:1.1.0
helm upgrade testball deploy/helm/testball -n qa --reuse-values --set image.tag=1.1.0
kubectl -n qa rollout status deploy/testball
```

Несколько реплик обновляются безопасно: миграции применяет одна реплика под блокировкой PostgreSQL, остальные ждут. Новые поды не считаются готовыми (`/readyz`), пока миграции не закончатся, поэтому старые поды обслуживают пользователей до конца. Миграции в минорных версиях только добавляют таблицы и колонки, так что старые поды работают с обновлённой базой, пока их не заменят.

## После обновления

- «Пользователи → О системе»: новая версия, число миграций, строка в «Истории обновлений».
- Откройте пару проектов, прогон и отчёт — если что-то не так, смотрите лог: `docker compose logs app` или `kubectl logs`.

## Если обновление не удалось

**Сервер не запускается, в логе ошибка миграции.** Миграция выполняется в транзакции: если она упала, база осталась как была. Пришлите в поддержку текст ошибки и строку «Скопировать для поддержки» со страницы «О системе» (или версию из лога). Можно вернуть прежний образ — он запустится, потому что база не изменилась.

**Обновление прошло, но новая версия работает плохо, нужно назад.** Просто запустить старый образ нельзя: сервер откажется стартовать с сообщением «База уже обновлена более новой версией TestBall». Это защита: старый код не знает новых таблиц и колонок и может испортить данные. Порядок отката:

1. Остановите приложение.
2. Восстановите базу из копии, снятой **до** обновления (README, «Шаг 8. Резервные копии»), в пустую базу.
3. Запустите прежнюю версию.

Всё, что пользователи сделали между обновлением и откатом, при этом потеряется. Если это неприемлемо, лучше дождаться исправления (патч-версии) и обновиться вперёд.

`ALLOW_DOWNGRADE=1` отключает проверку. Используйте только по указанию поддержки.

## Для разработчиков: выпуск версии

1. Поднимите версию: `npm version minor --no-git-tag-version` (и то же в `web/`), `version` и `appVersion` в `deploy/helm/testball/Chart.yaml`, `image.tag` в `values.yaml`. Тест «версии согласованы» проверит, что ничего не забыто.
2. Перенесите раздел «не выпущена» в CHANGELOG.md под номер версии с датой.
3. Новые миграции — только следующими номерами (`019_….sql`); уже выпущенные миграции не меняются никогда. В минорных и патч-версиях миграции только добавляют (таблицы, колонки с значением по умолчанию, индексы), чтобы старые поды работали во время обновления.
4. Тег `vX.Y.Z` на коммите: CI проверит, что тег совпадает с версией в package.json, соберёт и опубликует образ.
