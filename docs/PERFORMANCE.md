# Производительность и нагрузочное тестирование

## Стенд

`scripts/loadgen.js` создаёт большой проект прямо в базе (SQL, без API):

```sh
DATABASE_URL=postgres://… node scripts/loadgen.js --key=BIG --cases=50000 --runs=20 --bugs=10000 --autoruns=500 --tests=2000
```

Это 50 тыс. кейсов, 1 млн результатов ручных прогонов, 10 тыс. багов и 1 млн результатов автотестов — генерация занимает около 35 секунд. Только для стендов: в рабочую базу не запускать.

## Замер ключевых запросов

```sh
node scripts/bench.js --url=http://localhost:3000 --login=admin --password=… --key=BIG --n=20
```

Результат на стенде выше (PostgreSQL 16, 2 vCPU, одна реплика приложения, ответы со сжатием):

| Запрос | p50 | Ответ |
|---|---|---|
| Общее состояние `/api/state` | 55 мс | 1 КБ |
| Состояние проекта (один раз при открытии проекта) | 1,3 с | 1,3 МБ gzip |
| Результаты прогона на 50 тыс. кейсов | 1,0 с | 0,9 МБ gzip |
| История кейса | 6 мс | 3 КБ |
| Страница списка кейсов с фильтром | 26 мс | 57 КБ |
| Поиск кейсов (морфология) | 4 мс | 29 КБ |
| Глобальный поиск | 60 мс | 1 КБ |
| Список багов с фильтром | 4 мс | 35 КБ |
| Аналитика за 30 дней | 0,8 с | 14 КБ |

Для сравнения: до разделения состояния весь стенд уходил в браузер одним ответом на сотни мегабайт после каждого изменения у любого участника, а аналитика считалась 4 секунды.

Что сделано для этих цифр: состояние по проектам вместо общего, последний результат кейса хранится в самом кейсе (триггер), тексты кейсов не входят в состояние проекта, полнотекстовые индексы, индексы под «последний результат» и «был ли автотест», сжатие ответов, ETag.

## Нагрузка: k6

```sh
k6 run -e URL=http://localhost:3000 -e LOGIN=admin -e PASSWORD=… -e KEY=BIG -e VUS=50 load/k6.js
```

Сценарий: виртуальные тестировщики открывают прогон, отмечают результаты, ищут кейсы, смотрят историю; каждый десятый шаг перечитывает состояние проекта. Пороги: 95% лёгких запросов быстрее 300 мс, состояние проекта — 2 с, ошибок меньше 1%.

## Известные ограничения

- После любого изменения в проекте браузеры участников перечитывают состояние проекта целиком (1–1,5 с на стенде 50 тыс. кейсов). Следующий шаг — инкрементальные обновления (изменения с момента последней загрузки).
- Лимиты попыток входа считаются в каждой реплике отдельно (README, «Kubernetes»).
